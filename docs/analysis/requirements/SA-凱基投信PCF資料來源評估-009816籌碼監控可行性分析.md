### 背景與問題

使用者想在 `config/watchlist.json.etfs` 新增 `009816`（凱基台灣TOP50，凱基投信發行、2026/2/3 上市之市值型 ETF）之籌碼變動監控，但查閱 `config/issuer_registry.json` 發現目前受支援的 8 家投信（元大、富邦、國泰、群益、野村、統一、安聯、復華）不含凱基投信——**此觀察正確**，凱基投信目前確實不在白名單內，也從未在既有 SA/SD 文件的查證輪次中出現過，是一個全新的投信機構。

**特別澄清（避免與既有設定混淆）**：專案中另有 `config/broker_branches.json` 出現「凱基-台北」（券商分點代碼 `1020`），那是**凱基證券**用於「三大法人／分點買賣超」功能的分點代碼，與本文件要評估的 ETF PCF 發行方**凱基投信**是完全不同的公司與功能模組，兩者不可混為一談。

本文件依現行「[新增投信 Adapter 之驗證 SOP](../../design/architecture/SD-ETF換倉資料來源方案評估-投信官網爬蟲-系統設計書.md)」（SD 文件第二輪新增）之 4 項檢核，實地查證凱基投信官網，評估是否有可行的擴充路徑。

**方法論限制須誠實揭露**：本次查證使用 `WebFetch` 工具（將頁面轉為 Markdown 後再摘要），該工具會清除 `<script>` 標籤與頁面內嵌的 JavaScript 變數，**無法像既有 SD 文件第六、十、十二、十五輪那樣，透過瀏覽器開發者工具的 Network 分頁實際攔截頁面背後呼叫的 JSON/AJAX API**。因此「頁面為動態載入」是本輪查證能確認的事實，但「背後有沒有底層資料 API、API 長什麼樣子」目前**尚未查明**，不能據此判定為技術不可行——這與既有文件中野村、國泰、群益、安聯投信**最初**用一般請求查證時的結論完全相同，這四家最終都是 Roy Chiang 用瀏覽器開發者工具／Postman 找到底層 API 後才翻案為「低～中複雜度可行」。

## 二、對照既有「新增投信 Adapter 之驗證 SOP」逐項檢核

依 [SD 文件](../../design/architecture/SD-ETF換倉資料來源方案評估-投信官網爬蟲-系統設計書.md) 第二輪定義之 4 項 SOP 逐一檢核：

| # | SOP 檢核項目 | 本次查證結果 | 狀態 |
| :--- | :--- | :--- | :--- |
| 1 | URL 規則：能否用市場代碼直接組 URL，或需投信內部代碼對照？ | 需要 `fundID`（如 `J023`）內部代碼，`009816` 本身無法直接組出正確 URL | ⚠️ 需對照表，但**非阻塞**——同國泰／群益／野村／安聯／復華既有先例，這幾家最終都是靠一支「投信旗下全部基金清單」端點動態查得對照，不需人工維護靜態表 |
| 2 | 渲染方式：伺服器端渲染（可直接 `BeautifulSoup` 解析）或 JS/AJAX 動態載入？ | 頁面顯示「Loading...」，判斷為動態載入，但底層 API 尚未查得 | ❓ **待查**，本次查證方法論無法回答 |
| 3 | 交易日期欄位：頁面／回應是否有明確日期欄位可供既有日期防呆機制比對？ | 因看不到實際資料表格，無法確認 | ❓ **待查**，需等第 2 項解決後才能一併確認 |
| 4 | 服務條款：`robots.txt`／服務條款是否明確禁止自動化擷取？ | `robots.txt` 全站無 `Disallow`，初步無疑慮；服務條款全文本次未查 | 🟡 初步可行，服務條款全文比照既有慣例列為「上線前人工確認項」，非動工前阻塞項 |

**檢核結論：4 項中有 2 項（渲染方式、交易日期欄位）尚未確認，本次評估無法判定凱基投信為「可行」或「不可行」，僅能判定為「待確認」**——這正是既有 SOP 設計的意義：在查明前不預先假設結果，避免像復華投信第十三輪那樣，因參數格式問題被誤判為「已阻塞」，浪費後續重新查證的成本。

## 三、可行性評估細項

### 3.1 技術可行性：**未定，非「已阻塞」**

本專案目前已開通的 8 家投信中，除元大／富邦初次查證即確認伺服器端渲染外，其餘 6 家（國泰、群益、野村、統一、安聯、復華）**最初都經歷過與凱基投信本次相同的「一般請求查不到資料、疑似 SPA」階段**，之後全數靠瀏覽器開發者工具或 Postman 找到底層 JSON API 而翻案為可行，且複雜度多落在「低～中」。凱基投信重演相同結果的機率不低，但不能以此替代真正查證。

### 3.2 維護成本：與既有擴充模式一致

若第 2、3 項 SOP 確認可行，後續開發完全落在既有架構內：新增 `KgiPcfAdapter`（實作 `IssuerPcfProvider.fetch_holdings()`）、於 `ADAPTER_REGISTRY` 註冊一筆、`config/issuer_registry.json` 新增 `kgi` 區塊——**不需改動 `Fetcher`／`Analyzer`／`Notifier` 核心邏輯**，屬於既有「資料來源可替換、新增不需重構核心邏輯」擴充性策略的又一次直接套用，維護成本與其餘 8 家投信新增時相同，是線性增量而非架構負擔。

### 3.3 法遵與風險考量

`robots.txt` 全站無限制，且 PCF 依主管機關規定為 ETF 必須每日公開揭露之資訊，性質上與既有 8 家投信一致，風險低；服務條款全文之人工審視比照既有慣例列為上線前確認項。

## 四、若確認可行後的落地方式（比照既有 Adapter 慣例）

| 元件 | 內容 | 異動類型 |
| :--- | :--- | :--- |
| `src/issuer_pcf/kgi.py`（`KgiPcfAdapter`） | 實作 `fetch_holdings(etf_id, snapshot_date) -> list[dict]`，回傳鍵名 `component_stock_id`／`component_name`／`holding_shares`（可參考 `src/issuer_pcf/nomura.py` 作為「JSON API＋日期防呆」的撰寫範本） | 🔴 新增（待 SOP 第 2、3 項確認後才能動工） |
| `src/issuer_pcf/registry.py` | `ADAPTER_REGISTRY` 新增一筆 `"KgiPcfAdapter": KgiPcfAdapter` | 🟡 修改 |
| `config/issuer_registry.json` | 新增 `kgi` 區塊：`name`（凱基投信）、`adapter`（`KgiPcfAdapter`）、`pcf_url_template`、`etfs`（`["009816"]`）；`isEnabled` **建議初始設為 `false`**，比照安聯投信「技術可行性未確認前 `isEnabled` 維持 `false`」的既有慣例，待 PoC 查證完成、實測資料正確後才改 `true` | 🟡 修改（待實作完成後） |
| `config/watchlist.json` | `etfs[]` 加入 `"009816"` | 🟡 修改（**須等 `issuer_registry.json` 完成註冊後才能加入**，見下方提醒） |

**重要提醒**：目前 `config/issuer_registry.json` 尚無 `kgi` 對應項目，若現在就直接把 `009816` 加進 `watchlist.json.etfs`，會在 `ConfigLoader._validate()` 階段被既有白名單機制判定為設定錯誤而**中止程式啟動**（見 SD 文件「白名單錯誤訊息可讀性」設計，此為既定行為而非 bug）。因此在完成第五章 Step 1 查證之前，**不建議**先行修改 `watchlist.json`。

## 五、建議實施策略（分階段）

1. **Step 1（PoC 查證，需要真人以瀏覽器開發者工具介入，本次 WebFetch 方法論已證實無法自行完成）**：實際開啟 `https://www.kgifund.com.tw/Fund/RedemptionList?fundNo=J023`，於瀏覽器開發者工具 Network 分頁操作頁面（選取 009816、觸發資料載入），找出背後真正呼叫的 JSON/AJAX API 路徑、參數與回應結構——比照既有野村 `GetFundAssets`／國泰 `GetETFDetailStockList`／群益 `buyback`／安聯 `GetFundAssets` 的查證方式。同時留意頁面上其他基金（如「凱基台灣AI50」）背後是否共用同一支「凱基投信旗下全部基金清單」對照端點（同 `GetFundList`／`GetETFList`／`GetFundOverview` 模式），若有，可動態解決 `fundID`↔市場代碼對照問題，不需人工維護靜態表。
2. **Step 2a（若查得可用 API）**：依查得結果補齊本文件 §二 SOP 剩餘 2 項，比照既有 8 家投信模式，正式開發 `KgiPcfAdapter`、註冊、設定並開通 `isEnabled`，`watchlist.json.etfs` 加入 `009816`。
3. **Step 2b（若查無可用 API，頁面確為純前端渲染且無底層資料端點）**：依本專案「不引入 Headless Browser」之既定架構原則，凱基投信在現行架構下應如中信投信之例明確列為「不可行」，而非停留在含糊的「待評估」，避免日後重複投入時間查證同一已有結論的項目。
4. **例外容錯**：沿用既有原則——即使凱基投信最終開通，單日解析失敗也僅該 ETF 略過（標記 `NO_DATA`/`ERROR`），不影響其餘關注清單項目。

## 六、待確認事項

- 是否存在「凱基投信旗下全部 ETF」動態代碼對照端點，取代人工維護 `fundID`↔市場代碼對照表。

- 若確認可行，是否一併評估凱基投信旗下其他 ETF（ETF 總覽頁已見「凱基台灣AI50」等），或本次僅限 `009816`，待 Roy Chiang 確認範圍。

## 七、結論與建議

**使用者的觀察正確**：凱基投信目前確實不在 `config/issuer_registry.json` 白名單內，也是全新查證的投信機構。但這代表「尚未查證」，不代表「已查證不可行」——本次 PoC 查證到的狀態（內部代碼對照、頁面動態載入、robots.txt 無限制），與野村／國泰／群益／安聯投信最初階段的查證結果一致，而這四家最終都被證實為低～中複雜度可行。

**建議**：暫不直接修改 `watchlist.json` 加入 `009816`（會導致程式啟動即報設定錯誤），先完成第五章 Step 1 的瀏覽器開發者工具查證，確認底層資料端點是否存在。**一旦查得可用 API，後續開發可完全套用本專案既有的 `IssuerPcfProvider` Adapter 慣例**（`nomura.py`／`allianz.py` 等既有寫法即為現成範本），不需要任何架構層級的新設計——這正是既有「資料來源可替換、新增不需重構核心邏輯」擴充性策略的又一次直接套用實例，技術路徑是通的，只是還差最後一哩的端點查證。
