### 背景與問題

原 SA/SD 文件將「證交所 PCF API」設計為 ETF 持股資料的**單一、統一**來源（一個端點涵蓋所有 ETF），SD 文件 §六 待確認事項 #1 當時已註記「端點路徑/欄位是否一致待開發階段驗證」；實際開發後確認**免費／無金鑰即可穩定取用的證交所 PCF API 端點事實上不存在**，此方案在資料來源端即被卡住，與分點買賣超（FinMind，已有可行的免費 API）情況不同。

本次要評估的替代方案：**放棄「單一統一 API」的假設，改為依使用者關注清單（`config/watchlist.json` 的 `etfs[]`），逐一對應該 ETF 的發行投信，直接向該投信官網每日公告的 PCF 頁面取得持股資料**，再組合為與既有 `ETF_HOLDING_RECORD` 相同的結構，餵入既有 Analyzer/Notifier 流程。以使用者提出的例子：0050 發行商為元大投信，其官網每日公開 PCF，理論上可直接取用。

## 一、實地查證結果（Proof of Concept 調查）

為避免評估流於臆測，實際查證了兩家投信官網的 PCF 揭露頁面：

| 投信 | ETF 範例 | 查證網址 | 呈現方式 | 查證結果 |
| :--- | :--- | :--- | :--- | :--- |
| 元大投信 | 0050 | https://www.yuantaetfs.com/tradeInfo/pcf/0050 | HTML 表格（伺服器端渲染） | 頁面明確標示「交易日期：2026/08/07」，表格含股票代碼、股票名稱、股數等欄位，且提供「匯出 excel」按鈕；但表格有「展開」互動元件，**尚未確認**展開前後是否為同一份 HTML 內容（僅 CSS 摺疊）或需額外請求 |
| 富邦投信 | （通用 PCF 頁） | https://websys.fsit.com.tw/FubonETF/Trade/Pcf.aspx | HTML 表格（伺服器端渲染） | 頁面存在且格式類似（股票代碼、名稱、股數、查詢日期），但**未帶入特定 ETF 代碼時預設顯示的是另一檔基金**（查得的成分股為美股），代表此網址需搭配 ETF 專屬 query 參數才能導向正確標的，且**未見直接的 CSV/Excel 下載連結** |

**初步結論：** 至少兩家頭部投信官網確實各自公開每日 PCF，且都是傳統伺服器端渲染的 HTML 表格（非純 JS 前端渲染的 SPA），技術上屬於「較容易解析」的類型，初步驗證了使用者提出方向的可行性。但也同時證實了預期中的風險：**每家投信的網址規則、頁面結構、資料完整性呈現方式都不同**，無法用同一套解析邏輯套用所有投信。

## 二、方案比較

| 比較項目 | 原方案：證交所 PCF API（單一端點） | 新方案：依投信官網逐一爬取 |
| :--- | :--- | :--- |
| 涵蓋範圍 | 理論上全市場 ETF 一次涵蓋 | 僅涵蓋「關注清單中，且已開發對應投信 adapter」的 ETF |
| 資料來源數量 | 1 個 | N 個（等於關注清單中出現的投信家數） |
| 可用性 | 未找到免費穩定端點，已卡關 | 已查證至少 2 家投信官網公開頁面可正常存取，免登入免金鑰 |
| 維護成本 | 低（單一介面） | 隨投信家數線性增加；任一家官網改版即需個別修正 |
| 失效方式 | 有明確的 HTTP 錯誤碼 | 通常是「靜默失效」——頁面還能開，但表格結構已變、解析結果錯誤或為空，不易第一時間察覺 |
| 與需求本質的契合度 | 過度設計（本需求本來就是依關注清單查詢，不需要全市場資料） | 完全貼合「依關注清單查詢」的實際需求 |

**評估結論：新方案在「可用性」上明顯優於已卡關的原方案，且範圍限制（只涵蓋關注清單投信）並非缺點，而是與 FR-1.2「支援輸入指定 ETF 代碼」的設計精神本就一致。** 真正的代價是維護成本從「串接一個 API」變成「維護 N 個網站的個別爬蟲」，需要在第五章的分階段策略中管理。

## 三、可行性評估細項

### 3.1 技術可行性：可行

- 已查證兩家頭部投信皆屬伺服器端渲染 HTML，`requests` + `BeautifulSoup`/`lxml` 應可直接解析，不必然需要 Headless Browser（Playwright），可維持現行 SD 文件「輕量批次腳本、無額外重型相依」的設計原則。
- 元大頁面有「匯出 excel」按鈕：**建議優先查出該按鈕實際呼叫的下載端點**（通常是帶查詢參數的固定 URL，直接回傳結構化 Excel/CSV），比解析畫面上的 HTML 表格更不受版面調整影響，穩定性更高，此為 Phase 0 PoC 的第一個查證項目（見第六章）。
- 元大表格的「展開」元件、富邦頁面需要的 query 參數，皆須在 PoC 階段以瀏覽器開發者工具的 Network 分頁確認**該頁面背後是否呼叫獨立的 JSON/AJAX API**——若有，直接呼叫該 API 會比解析渲染後的 HTML 更穩定，是實作時應優先嘗試的路徑。

### 3.2 維護成本：主要風險與代價來源

- 每家投信網站的網址規則、欄位命名、資料呈現方式都不同（已於第一章查證中驗證），無法共用單一套解析邏輯，只能以「每個投信一個 adapter」的方式個別開發。
- 任一投信網站改版，會讓對應 adapter **靜默失效**（頁面仍可開啟，但解析結果錯誤或為空），比原方案「呼叫 API 得到明確錯誤碼」更難察覺，需要額外的健全性檢查機制（見第六章）。
- 每次使用者在關注清單新增一檔「目前尚無對應 adapter 之投信」發行的 ETF，就需要新開發一次，屬於漸進式成本；但這與 SA 文件既有「擴充性策略」（資料來源需可替換、新增不需重構核心邏輯）的設計原則相符，不是新增的架構負擔。

### 3.3 法遵與風險考量

- PCF（申購買回清單）依主管機關規定為 ETF 必須每日公開揭露之資訊，供全體投資人查閱，非個資、非付費會員限定內容，抓取本身在**資料性質**上風險低。
- 建議遵守以下原則以降低風險，並應納入正式驗收標準：
  - 低頻率請求（比照原方案每交易日一次即可，不高頻輪詢）。
  - 設定合理識別性的 User-Agent，不偽裝一般瀏覽器行為。
  - 僅供個人分析使用，不對外公開轉售原始頁面內容。
- **待確認事項**：正式採用前應逐一檢視各投信官網的 `robots.txt` 與服務條款是否有明確禁止自動化擷取的條款；若某家明確禁止，該投信旗下 ETF 應排除於自動化清單外，改為人工週期性確認或尋找其他公開管道（如公開資訊觀測站）替代，不強行爬取。

## 四、對既有 SA/SD 文件的影響分析

好消息：本次變更**只影響 Fetcher 模組取得 ETF 持股資料的手段**，只要輸出仍符合既有 `ETF_HOLDING_RECORD` 資料結構，Analyzer（雙日持股比對分類）與 Notifier（推播格式化）完全不受影響，不需重新設計。

| 受影響文件/章節 | 原設計 | 建議變更 |
| :--- | :--- | :--- |
| SA §3.1 FR-1.2 | 「透過證交所 API 抓取 ETF 代碼對應的持股清單」 | 改為「透過該 ETF 發行投信官網之每日 PCF 公告頁面取得」 |
| SA §3.1 資料來源對照表 | 單一列「證交所 PCF API」 | 改為「ETF 代碼 → 發行投信 → 官網 PCF 頁面（或其底層資料端點）」對照表，隨關注清單擴充 |
| SA §一 關鍵設計原則（擴充性策略） | 資料來源需可替換 | 沿用不變，本次變更正是此原則的實例 |
| SD §一 架構圖 | `TWSE["證交所 PCF API"]` 單一外部節點 | 改為依關注清單動態展開的多個「投信官網」節點（如元大、富邦…） |
| SD §四 `TwsePcfClient` | 單一 Client 類別 | 改為 `IssuerPcfProvider` 介面 + 各投信專屬 Adapter（`YuantaPcfAdapter`／`FubonPcfAdapter`…），Strategy Pattern，符合現有「Fetcher 建構子可注入 Client」的既有擴充設計 |
| SD §二 `config/watchlist.json` | `etfs[]` 僅列 ETF 代碼 | 需新增 `config/etf_issuer_mapping.json`：ETF 代碼 → 發行投信 → 對應 adapter 類型；`etfs[]` 中若出現尚無對照的代碼，啟動階段即應報 `CONFIG_INVALID`（沿用既有錯誤碼設計） |
| SD §六 待確認事項 #1 | 「PCF API 主動/被動 ETF 端點差異待確認」 | 轉化為「各投信 adapter 需個別驗證通過」，待確認範疇不變但單位從「API 版本差異」變成「投信官網差異」 |
| Analyzer／Notifier | — | **不受影響**，維持現有設計 |

## 五、建議實施策略（分階段）

1. **Phase 0（PoC）**：先以使用者最優先關注的 0050（元大投信）走完「抓取 → 比對 → 推播」全流程一次，並在此階段查明元大「匯出 excel」按鈕背後的實際下載端點與資料完整性（是否含全部 50 檔成分股），驗證整體方案在真實環境下可行後再擴大範圍。
2. **Phase 1（正式導入）**：以 `IssuerPcfProvider` 介面取代現有 `TwsePcfClient` 作為預設路徑，實作 `YuantaPcfAdapter`；證交所 PCF API 若日後真的找到可用的免費管道，可保留為次要/備援資料源，非必要條件。
3. **Phase 2（漸進擴充）**：依使用者關注清單實際新增的 ETF，逐一開發對應投信的 adapter（富邦、國泰、中信…），每新增一家投信即為一次獨立的小型開發任務，符合既有擴充性設計，不需一次做齊全市場投信。
4. **例外容錯**：沿用 SA §一「任何單一資料來源失敗需捕捉並記錄 Log、不得中斷整體流程」原則——單一投信官網爬蟲失效時，僅該 ETF 當日的換倉分析從報告中略過（標記 `NO_DATA`/`ERROR`），關注清單中其他 ETF 與分點資料仍正常產出與推播。

## 六、待確認事項（留待 PoC / SD / 實作階段）

- 元大「匯出 excel」按鈕實際下載端點、回傳格式，是否需要額外 headers/cookie/session（若需要，會提高維護複雜度，需重新評估優先度）。
- 元大表格「展開」互動：完整成分股清單是否已存在於原始 HTML（僅 CSS 摺疊，可直接解析）或需額外呼叫 AJAX 端點才能取得展開後的完整清單。
- 富邦（及其他投信）頁面對應各 ETF 代碼的正確 query 參數規則。
- 各投信網站 `robots.txt`／服務條款是否有明確禁止自動化擷取，需逐家審視後才正式排入自動化清單。
- **解析健全性檢查機制**：建議新增「解析結果與前一日相比異常（如成分股數量驟降為 0 或劇烈變化）時標記警示」，避免投信網站局部改版導致爬蟲解析出錯誤資料卻被誤判為正常的 `OK` 狀態送入 Analyzer。
- 是否需要「連續 N 天爬取失敗」的額外告警（不同於單日失敗僅記 Log），及早提醒維運人員某投信 adapter 已因改版而失效。

---

## 七、結論與建議

**建議採用。** 原「證交所 PCF API 單一端點」方案已確認卡關，而本次查證已用真實網頁證實使用者提出的方向（依投信官網逐一取得 PCF）技術上可行，且變更範圍侷限在 Fetcher 模組，不影響已完成的 Analyzer/Notifier 邏輯與測試。

唯一需要事先對齊的預期是：**這是把「串接一個免費 API」換成「維護 N 個投信網站爬蟲」的取捨**——可用性換取了維護負擔，且每個投信各自的頁面改版都可能造成靜默失效。建議先以 0050（元大投信）完成 Phase 0 PoC 驗證整體可行性後，再依使用者實際關注清單逐步擴充其他投信，而非一次到位涵蓋所有投信機構。
