## 提案全貌

| 項目 | 現行設計 | 提案設計 |

## 各項決策現況

### 決策 1：08:45 是否安全？能否提早到 08:00～08:30？——~~待確認~~ ✅ 第二輪：**提案不採用，本項疑慮不再需要解答**

2026-08-24（週一）09:18 對各投信即時查詢的結果：

| 投信 | 查上週五（08-21，最近交易日） | 查當天（08-24，交易中） | 觀察 |
| :--- | :--- | :--- | :--- |
| 元大 | — | — | 已有明確證據：公告約在前一天 16:30～17:00 結算完成（回應內建 `upddate` 時間戳欄位），08:45 對元大有 12 小時以上緩衝，**可視為安全** |
| 群益 | `pcf.date1=2026-08-21` 精準對上 | `pcf.date1=2026-08-24`，但持股股數（`share`）跟週五**完全相同**（如富邦金皆為 608,790,000 股），只有 NAV／權重數字不同 | 推測「持股清單」本身也是收盤才更新，週一早上看到的是「用即時報價重新估值舊清單」；**尚未證實清單本身確切更新時間** |
| 復華 | `dDate=2026/08/21` 有資料 | 查 `2026/08/24` 完全查無資料 | 至少證實 09:18 這個時間點復華還沒開出「今天」的殼，但**不代表週五的資料是幾點準備好的**，未測到確切時間 |
| 國泰 | 有資料 | 有資料，但逐筆比對跟週五完全一樣 | 國泰本無驗證機制，此結果無法證明時間點 |
| 統一 | — | — | 官網本身無日期查詢能力（見 [SD-ETF換倉歷史日期回補機制-系統設計書.md](./SD-ETF換倉歷史日期回補機制-系統設計書.md) 分類 A），時間點調整對它沒有實質幫助 |

**待解決的根本限制：** 這次測試是「週一交易中」單一時間點的快照，沒有「同一天開盤前 vs 收盤後」的對照組，無法回答「復華／群益到底幾點更新完上一個交易日的資料」。要真正回答「能否提早到 08:00～08:30」，需要**跨日對照測試**（例如某天 08:00 與 08:45 各查一次，比對前一天收盤資料是否都已到位）。

### 決策 3：Commit message 改用查詢日期——**已確認並完成**

**額外發現的既有問題：** 原本 `.github/workflows/daily-chip-monitor.yml` 的 commit message 固定用 `$(date +'%Y-%m-%d')`（workflow 執行當下的日期），但手動觸發補跑指定日期（`workflow_dispatch` 的 `date` 輸入）時，資料其實是別的日期的，commit message 卻照樣寫執行當下的日期——**這是本次討論前就存在的既有落差**，不只是為了配合本提案才需要修正。

| 項目 | 異動 |
| :--- | :--- |
| 邏輯調整 | 新增 `id: run` 步驟輸出 `target_date`（優先採用 `workflow_dispatch` 的 `date` 輸入，否則才用執行當下日期），並改為**明確地**把這個值傳給 `python main.py --date "$TARGET_DATE"`，不再讓 `main.py` 自行決定要不要有 `--date` | 
| Commit message | `git commit -m "chore: 更新籌碼快照資料 $(date +'%Y-%m-%d')"` → `git commit -m "chore: 更新籌碼快照資料 ${{ steps.run.outputs.target_date }}"` |
| 附帶效益 | workflow 現在一律明確帶入 `--date`，未來若要把 `target_date` 預設邏輯改成「前一交易日」（決策 4），只需要調整這個步驟裡 `TARGET_DATE` 的計算方式，牽動範圍侷限在一處 |

異動類型：🟡 修改（`.github/workflows/daily-chip-monitor.yml`），無需對應測試（純 CI YAML 邏輯，非 Python 程式碼）。
